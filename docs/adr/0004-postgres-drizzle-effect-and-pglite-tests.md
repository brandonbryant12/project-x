# ADR 0004: PostgreSQL via Drizzle's Effect driver; PGlite runs tests in-process

- Status: Accepted
- Date: 2026-11-16

## Context

Content Studio pairs Drizzle with `@effect/sql-pg` through
`drizzle-orm/effect-postgres`. Its integration tests need Testcontainers and
Docker. That makes them slow, impossible to run in some sandboxes, and the
reason E2E runs on a single worker.

As of 2026-11-16:

- `drizzle-orm@1.0.0-rc.5` ships both `effect-postgres` (over `@effect/sql-pg`)
  and `effect-pglite` (over `@effect/sql-pglite`).
- Both drivers expose the same `PgEffectDatabase` query surface.
- A spike confirmed that queries, transactions and rollback on failure behave
  as expected on PGlite (in-process WASM Postgres).

## Decision

**Production and development use PostgreSQL 17 through
`drizzle-orm/effect-postgres` on `@effect/sql-pg`. Tests run the same schema,
migrations and repositories against an in-process PGlite database through
`drizzle-orm/effect-pglite`.**

- Repositories depend on a `Db` service typed as the shared
  `PgEffectDatabase` surface, not on a particular driver.
- Migrations are generated by `drizzle-kit` into `packages/db/drizzle/`. They
  are forward-only, and both Postgres and PGlite apply them.
- IDs are prefixed, branded strings (`per_…`, `skl_…`) generated in the
  application. Timestamps are `timestamptz`. Statuses are `text` checked by
  the domain Schema, not `pgEnum`, so a lifecycle change does not need an
  enum migration.
- The database enforces whatever it can: foreign keys, CHECK constraints, and
  partial unique indexes such as "one active plan per person".
- Every tenant-owned table has a `tenant_id` column, and composite foreign
  keys include it where practical (see [ADR 0009](./0009-row-level-tenancy.md)).

## Alternatives considered

- **Testcontainers only.** Highest fidelity, but it needs Docker and is slow.
  We keep a small `test:pg` lane that runs the same suites against real
  Postgres when needed.
- **Raw `@effect/sql` with Schema-decoded rows.** Less magic, but agents write
  typed Drizzle queries more reliably, and drizzle-kit gives us migration
  diffs.
- **Prisma.** It has no Effect integration and generates a heavier client.

## Consequences

- `pnpm test` needs no Docker. Each test file gets a fresh, migrated database
  in milliseconds.
- PGlite is single-connection and has small behavioral differences, such as
  some extensions and concurrency. Tests that depend on locking or concurrency
  belong in the `test:pg` lane.
- drizzle-orm 1.0 is a release candidate. Pin it exactly in the catalog.

## Amendment (2026-11-16)

- **Production and local development use PostgreSQL 18.** PGlite 0.5 runs the
  PostgreSQL 18 engine, so tests and production share a major version. Compose
  runs `postgres:18-alpine`. `DATABASE_URL=pglite:<dir>` remains available for
  quick experiments only.
- **Rules drizzle-kit cannot express live in a hand-written `*_integrity`
  migration:** append-only and frozen-after-sign triggers, `btree_gist`
  exclusion constraints, and one circular FK. Each is proven by
  `packages/db/src/integrity.test.ts`.
- **Composite tenant foreign keys are used everywhere, not only "where a real
  risk"** (see the ADR 0009 amendment).
